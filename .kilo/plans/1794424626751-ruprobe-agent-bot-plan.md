# RuProbe — план реализации

Telegram-бот для проверки доступности IP, доменов и диапазонов с точки наблюдения
«регион + оператор», с классификацией отказов по модели ТСПУ.

Контекст и обоснование решений: `docs/tspu-model.md` (модель зондов и четыре класса отказа),
`docs/stack.md` (зафиксированные версии).

---

## 1. Зафиксированные решения

| Решение | Выбор | Почему |
|---|---|---|
| Язык агента-зондов | **Go 1.27.4** | конкурентность, таймауты, сырой контроль над TLS |
| Язык интерфейса | **Python 3.12 + aiogram 3.31.0** | Bot API 10.3, rich messages |
| Роль Go | **вариант B**: без постоянного состояния, чистый исполнитель проб | воркер можно вынести на другую машину заменой адреса |
| Роль Python | владеет БД, моделями, классификацией, Telegram | вся персистентность и логика в одном месте |
| ORM | **SQLAlchemy 2.0 async** (на стороне Python) | модели под сущности из `docs/tspu-model.md` |
| БД | **SQLite в режиме WAL** | одна машина, один регион, обратимо мигрирует на PostgreSQL |
| Миграции | **Alembic** | схема будет меняться при добавлении операторов |
| Связь Python → Go | **асинхронная очередь job-id**, опрос статуса | будущие операторы и регионы, не держим HTTP на долгих пробах |
| Очередь в Go | **`chan Job` + пул горутин**, статусы в памяти с TTL | состояние эфемерное, история всё равно в SQLite |
| Развёртывание | **один `compose.yaml`**, оба сервиса на одной машине | требование пользователя |
| YAML-шаблоны | **`x-` анкоры** (`&common` / `*common` / `<<:`) | требование пользователя |
| Ключ `version:` | **не использовать** | устарел, выдаёт warning |
| Стриминг прогресса | `sendRichMessageDraft` (черновик 30 с) + финальный `sendRichMessage` | лимит 32768 символов, 500 блоков |

### Уточнение по aiogram

В требованиях было «aiogram 10.3» — такой версии нет. **aiogram 3.31.0**, а **10.3 — это версия
Bot API**. Установка `pip install aiogram==3.31.0`; требование `Python >=3.10, <3.15`.
Подробности в `docs/stack.md`.

## 2. Архитектура

```
┌─────────────── Docker network: ruprobe ───────────────┐
│                                                        │
│  ┌─────────────────────┐      ┌──────────────────┐    │
│  │  bot (Python 3.12)  │      │ agent (Go 1.27.4)│    │
│  │                     │ HTTP │                  │    │
│  │  aiogram 3.31.0     │─────►│  probe engine    │    │
│  │  SQLAlchemy 2.0     │◄─────│  chan + workers  │    │
│  │  SQLite (WAL)       │ poll │  in-memory TTL   │    │
│  └─────────┬───────────┘      └──────────────────┘    │
│            │                          │                │
└────────────┼──────────────────────────┼────────────────┘
             │                          │
       Telegram API              пробы в интернет
```

**Границы ответственности:**

- `agent` (Go) — знает только «выполнить зонды для цели и вернуть факты». Не знает про
  Telegram, пользователей, регионы, историю. Никакой БД.
- `bot` (Python) — знает про пользователей, точки наблюдения, историю, классификацию,
  рендеринг. Не выполняет сетевых проб сам.

**Источник правды — SQLite в Python.** Go при рестарте теряет in-flight задания, и это
допустимо: постоянная история уже записана. Python обязан помечать такие задания как
упавшие, иначе в Telegram навсегда повиснут прогресс-сообщения.

## 3. Контракт HTTP между Python и Go

Внутри docker-сети, наружу не публикуется.

```
POST /probe/batch      → создаёт задание
  { "targets": ["1.2.3.4", "example.com", "5.6.7.0/29"],
    "probes": ["dns", "tcp", "sni", "throughput", "udp", "icmp", "neighbors"],
    "timeout_ms": 5000,
    "throughput_bytes": 1048576 }
  → 202 { "job_id": "..." }

GET  /jobs/{job_id}    → статус и, при готовности, результаты
  → { "status": "running|done|failed",
      "progress": { "completed": 12, "total": 40 },
      "results": [ ProbeResult, ... ] }

GET  /health           → liveness
```

`ProbeResult` — см. раздел 5. Батч, а не одна цель: диапазон не превращается в тысячи
HTTP-запросов.

## 4. Зонды (Go) — по `docs/tspu-model.md`

Каждый зонд возвращает структурированный факт, а не булево «доступно».

| Зонд | Реализация | Ключевое |
|---|---|---|
| `dns` | системный + публичный резолвер | различает подмену / NXDOMAIN / REFUSED / SERVFAIL / drop |
| `doh` | DoH-запрос | расхождение с открытым DNS — самостоятельный сигнал |
| `tcp` | `net.Dialer` с дедлайном | **RST и timeout — разные события**, фиксируются явно |
| `tcp_alt_ports` | connect на 80/8080/8443 | правило по порту vs по IP |
| `sni` | отправка ClientHello с заданным SNI **без завершения handshake** | проходит ли ClientHello |
| `sni_control` | тот же IP, **другой** SNI | блокировка по домену vs по адресу |
| `tls_full` | полный handshake + HTTP(S) | сквозная доступность, RST vs timeout |
| `throughput` | N байт за T секунд | **деградация capacity не видна без этого зонда** |
| `udp` / `quic` | UDP probe, QUIC Initial | блокировка транспорта, QUIC-лист |
| `icmp` | echo | базовая живость, отделяет «сеть мертва» |
| `neighbors` | пинг адресов из /24, /16, AS | адресное правило vs префикс/CDN |

**Технические заметки:**

- `sni`-зонд требует контроля над ClientHello — стандартный `crypto/tls` не даёт остановиться
  после отправки. Планировать слой билдера ClientHello сразу (или `utls`).
- `tcp`-зонд должен использовать `net.Dialer.Control` для точной фиксации RST.
- Все зонды принимают `context.Context` с дедлайном; батч имеет общий дедлайн.

## 5. Модель данных (Python, SQLAlchemy 2.0 async)

Соответствует сущностям из `docs/tspu-model.md`.

```
ObservationPoint   id, region, operator, name, created_at
                   — точка наблюдения, входит в первичный ключ результата

Target             id, kind(net|domain|range|cidr), value, created_at
                   — нормализованная цель

Check              id, observation_point_id, target_id, status, created_at, finished_at
                   — один запуск, объединяет результаты по всем целям батча

ProbeResult        id, check_id, target_value,
                   rtt_ms, reset_received, timeout_happened,
                   throughput_bps, retransmits,
                   raw JSON  — все факты зондов

Verdict            id, probe_result_id, klass, confidence, signals JSON, created_at
                   — классификация, klass ∈ четыре класса отказа + "unavailable_other"

Subscription       id, user_id, target_id, schedule, created_at
                   — регулярные проверки (на будущее)
```

**`Verdict.klass`** — значения из модели: `block_l3l4`, `block_sni`, `degradation`,
`dns_interference`, `unavailable_other`.

**`Verdict.confidence`** — обязательное поле. По разделу 5 `docs/tspu-model.md` бот **не
выдаёт детерминированный вердикт**, только вероятностную классификацию с набором
сработавших сигнатур, точкой наблюдения и временем.

**`ObservationPoint` в первичном ключе** — не метаданные. Один и тот же ресурс штатно ведёт
себя по-разному у разных операторов.

## 6. Задачи (порядок исполнения)

### Фаза 1 — фундамент

1. **Структура репозитория**
   ```
   agent/          go.mod (go 1.27.4), cmd/, internal/probe/, internal/queue/, internal/httpapi/
   bot/            pyproject.toml, src/ruprobe_bot/, alembic/
   docs/           tspu-model.md, stack.md (уже есть)
   compose.yaml
   .env.example
   ```
2. **`agent/go.mod`** — модуль, зависимость только `golang.org/x/net` (и `utls`, если нужен).
3. **`bot/pyproject.toml`** — `aiogram==3.31.0`, `sqlalchemy[asyncio]`, `aiosqlite`, `alembic`,
   `pydantic-settings`, `httpx`. Указать `requires-python = ">=3.10,<3.15"`.

### Фаза 2 — агент (Go)

4. **Типы зондов и результат** — `ProbeResult` со всеми полями из раздела 5.
5. **Очередь**: `chan Job`, пул горутин (число из конфига), `map[jobID]jobState` под
   `sync.RWMutex`, TTL-сборщик для завершённых заданий.
6. **Зонды по одному**, начиная с `tcp`, `dns`, `icmp` — они проще и сразу дают данные.
7. **`sni`-зонд** — билдер ClientHello, остановка после отправки.
8. **`throughput`-зонд** — замер с подсчётом retransmit.
9. **HTTP API** — `POST /probe/batch`, `GET /jobs/{id}`, `GET /health`.
10. **Юнит-тесты** на классификацию фактов (RST vs timeout) и на TTL-очистку.

### Фаза 3 — бот (Python)

11. **Настройки** через `pydantic-settings` из env.
12. **Модели SQLAlchemy 2.0 async** + первая миграция Alembic.
13. **`PRAGMA journal_mode=WAL` и `busy_timeout`** при инициализации соединения — обязательно,
    иначе `database is locked` при параллельных пробах.
14. **Клиент Go-воркера** (`httpx`): создать задание, опрашивать статус с backoff.
15. **Классификатор** — правила «сигнатуры → класс + confidence» по `docs/tspu-model.md`.
16. **aiogram**: роутеры, команды, FSM для ввода цели.
17. **Rich messages** — таблица результатов, сводка, сноски. Короткие реплики через
    `sendMessage`, отчёты через `sendRichMessage`.
18. **Восстановление при рестарте Go**: при старте Python помечать зависшие проверки как упавшие.

### Фаза 4 — инфраструктура

19. **`compose.yaml`** — единый файл, `x-` анкоры, **без ключа `version:`**:

    ```yaml
    x-common: &common
      restart: unless-stopped
      logging:
        driver: json-file
        options: { max-size: "10m", max-file: "3" }

    services:
      agent:
        <<: *common
        build: ./agent
      bot:
        <<: *common
        build: ./bot
        depends_on: [agent]
    ```

20. **`Dockerfile`** для каждого сервиса, multi-stage для Go.
21. **`.env.example`** — `BOT_TOKEN`, `AGENT_URL`, `DB_PATH`.
22. **Проверка**: `docker compose config` — убедиться, что анкоры развернулись правильно
    (мердж поверхностный, ключи молча перезаписываются).

## 7. Риски и подводные камни

| Риск | Митигация |
|---|---|
| `<<: *anchor` — **поверхностный** мердж, вложенные ключи затираются целиком | Проверять `docker compose config`; не пытаться переопределять одно поле внутри общего блока |
| Анкоры **не работают между файлами** | Держать один `compose.yaml`, не разносить на override-файлы |
| `crypto/tls` не даёт остановиться после ClientHello | Слой билдера ClientHello планировать сразу, не как рефакторинг |
| Connect-проба не видит деградацию | Отдельный `throughput`-зонд обязателен |
| `database is locked` в SQLite | WAL + `busy_timeout`; БД трогает только Python |
| Зависшие проверки после рестарта Go | Python при старте помечает незавершённые как упавшие |
| Go 1.26.4 установлен, нужен 1.27.4 | `winget install GoLang.Go` (в 1.27.3/1.27.4 правки безопасности `net/http`, `crypto/tls`) |
| Compose 5.1.4 устарела (актуальна 5.7.1) | Обновить Docker Desktop |
| Ложные срабатывания классификации | Только вероятностный вердикт + сигнатуры; не утверждать причину |

## 8. Валидация

**Агент:**
- `go build ./...` и `go vet ./...` на Go 1.27.4;
- юнит-тесты на различение RST и timeout, на TTL-очистку статусов;
- ручной `curl` против `POST /probe/batch` + `GET /jobs/{id}`.

**Бот:**
- миграции применяются с нуля: `alembic upgrade head`;
- классификатор на синтетических наборах фактов — каждый из четырёх классов распознаётся;
- rich-сообщение с таблицей не превышает 32768 символов и 500 блоков.

**Интеграция:**
- `docker compose config` — анкоры развернулись корректно;
- `docker compose up` — оба сервиса поднялись, `bot` видит `agent` по имени сервиса;
- прогон трёх сценариев: живой домен, заведомо недоступный IP, диапазон /29;
- рестарт `agent` посреди проверки — `bot` корректно помечает проверку упавшей.

## 9. Границы (вне рамок)

Согласно разделу 5 `docs/tspu-model.md`:

- **Техники обхода не реализуются** — фрагментация ClientHello, анти-DPI, туннелирование.
  Проект только наблюдает доступность.
- Реализация сейчас — **один регион, один оператор**. Мультиоператорность заложена в схему
  (`ObservationPoint`), но интерфейс для её управления не делается.
- Расписания/подписки — таблица заведена, логика планировщика не реализуется.
- PostgreSQL не внедряется; миграция обратима заменой строки подключения.
