# RuProbe — план интеграции с antifilter.network: реестр как предфильтр

## 1. Цель

Добавить проверку «IP/префикс в реестре блокировок» (источник — списки antifilter.network)
как **первый шаг прогона**: сначала смотрим базу, потом прогоняем зонды.

Семантика по запросу пользователя:

- адрес есть в реестре → «с высокой вероятностью в бане» → проверка продолжается зондами,
  чтобы подтвердить/опровергнуть фактом сети и выбрать класс;
- адреса нет в реестре → прогон зондов как обычно, реестр ничего не добавляет.

Принципиальное ограничение, переносимое из предыдущего плана (раздел 4
`1794880000000-ruprobe-ip-probe-fix-plan.md`) с уточнением:

- реестр — это **аннотация и предфильтр очередности**, но **не сигнал классификатора**:
  membership не меняет веса сигнатур и не поднимает уверенность;
- класс по-прежнему ставится только по живым зондам; реестр даёт «априорную вероятность»
  и пометку в отчёте, но не вердикт.

Не цель этого плана: BGP-сессия с antifilter.network, VPN, проксирование проб,
обход DPI, мультиоператорность.

## 2. Что даёт antifilter.network (проверено 2026-11-16, страница /ip)

Публикует списки IP из реестра РКН в виде простых текстовых файлов:

| Файл | Формат | Объём (на дату проверки) |
|---|---|---|
| `ip.lst` | по одному префиксу на строку | 100364 префикса, 196358 адресов |
| `ipsmart.lst` | суммаризация /32-/23 | 21152 префикса |
| `ipsum.lst` | суммаризация по /24 | 21151 префикс |
| `subnet.lst` | крупные префиксы | 7 префиксов |
| `ip6.lst` | IPv6 | — |
| `uablacklist.lst`, `govno.lst`, `custom.lst` | доп. списки | — |

Источники: `reestr.rublacklist.net`, `github.com/zapret-info`, собственный резолв
заблокированных доменов. Цикл распространения адреса в DPI-листах ТСПУ 5–15 минут,
то есть списки запаздывают относительно фактической блокировки — это осознанное
ограничение и оно должно быть видно в отчёте (см. раздел 8, оговорки).

Базовые URL (проверить при реализации, формат одинаковый):

- `https://antifilter.download/list/ipsum.lst`
- `https://antifilter.download/list/ipsmart.lst`
- `https://antifilter.download/list/subnet.lst`
- (опционально) `https://antifilter.download/list/ip.lst`

## 3. Архитектурное решение: где живёт реестр

### 3.1 Хранение — в боте, не в агенте

Агент остаётся stateless и observation-only (docs/tspu-model.md): никаких списков,
никаких сетевых вызовов к antifilter.network из Go-кода. Реестр — это знание бота,
а не измерение агента.

- `bot/src/ruprobe_bot/registry.py` — новый модуль: загрузка, парсинг, проверка.
- Проверка цели выполняется **до** отправки батча агенту, синхронно по локальному набору префиксов.

### 3.2 Списки и их обновление

- По умолчанию используются два списка: `ipsum.lst` (префиксы /24 — основной рабочий
  набор) и `ipsmart.lst` (точная суммаризация /32-/23). `ip.lst` целиком (196k адресов)
  не грузим: `ipsmart` покрывает его суммаризацией с приемлемой точностью, а памяти
  и времени парсинга экономится много. `subnet.lst` опционален.
- Формат хранения в памяти: список `ipaddress.ip_network` объектов IPv4Network.
  Поиск — линейный по отсортированному списку с ранним выходом или через
  `ipaddress.collapsing`-группировку; при 20k+ сетей линейный поиск достаточен
  (единицы миллисекунд), бинарный поиск по `network_address` — оптимизация, не требование.
- Обновление: фоновая задача в боте (`asyncio.create_task` при старте), интервал
  `REGISTRY_REFRESH_S` (по умолчанию 3600 с = 1 час; цикл ТСПУ 5–15 мин, поэтому чаще
  смысла нет). ETag/Last-Modified — опционально, не требование.
- Отказоустойчивость: список не скачался → бот работает без реестра, в отчёте
  `в реестре: неизвестно (список недоступен)`. Реестр никогда не блокирует прогон.
- Кэш на диске: сохранять последний удачный список в `DB_PATH`-соседний файл
  (например `/data/registry_cache.txt`) — при рестарте бота без сети реестр остаётся.

### 3.3 Проверка адреса

Вход: цель из Telegram (домен, IP, CIDR, диапазон).

- Для домена: проверка по реестру **не выполняется** (домен не резолвим без пробы DNS,
  а делать resolve заранее — дублировать зонд). Домен идёт в прогон как есть.
- Для IP: проверяется сам `/32`.
- Для CIDR/диапазона: каждая развёрнутая цель проверяется отдельно; additionally
  можно проверить покрытие префикса целиком (например, /24 целиком в `ipsum.lst`
  → пометка «весь префикс в реестре»).

Результат проверки — структура:

```python
@dataclass
class RegistryHit:
    listed: bool
    source: str | None      # "ipsum.lst" / "ipsmart.lst"
    prefix: str | None      # конкретный префикс, который покрыл цель
    known: bool             # False = список не загружен, ответить нельзя
    checked_at: datetime
```

## 4. Изменение потока прогона: сначала база, потом зонды

Файлы: `bot/src/ruprobe_bot/handlers.py`, `bot/src/ruprobe_bot/service.py`.

Текущий поток: цель → `create_check` → `run_job` (зонды) → классификация.

Новый поток:

1. `create_check` как раньше.
2. **Шаг реестра** (быстрый, локальный): `registry.lookup(target)` → `RegistryHit`.
3. Вне зависимости от результата — зонды запускаются полностью (тот же набор
   по виду цели, что сейчас). Реестр **не сокращает** набор зондов и не пропускает
   прогон: «в реестре» ≠ «проверять не надо», а «проверить и подтвердить фактом».
4. Классификация получает факты зондов **плюс** `registry` как отдельный ключ в `raw`
   (см. 6.2) — но не как сигнал с весом.
5. Отчёт показывает пометку реестра.

Что меняется для пользователя:

- Пометка в черновике и в финальном отчёте: «адрес в реестре блокировок (ipsum.lst,
  префикс 177.3.212.0/22) — с высокой вероятностью под блокировкой; идёт проверка зондами».
- Черновик быстрее содержит полезную информацию: пометка реестра появляется сразу,
  до завершения зондов.

## 5. Интерпретация: как реестр сочетается с классом

Матрица исходов, которая фиксирует семантику:

| Реестр | Зонды | Итог |
|---|---|---|
| в реестре | жив, сигнатур нет | класс по зондам (unavailable_other/safe), пометка «в реестре, но не подтверждено зондами — возможно, список устарел или shared IP» |
| в реестре | заблокирован | класс по зондам (block_*), уверенность как обычно; реестр **не добавляет** вес, но пометка усиливает интерпретацию для человека |
| в реестре | сеть мертва | unavailable_other + «в реестре, но сеть до цели не жива — нельзя атрибутировать» |
| не в реестре | заблокирован | класс по зондам; пометка «не в реестре — блокировка не из публичного реестра РКН (иной механизм, свежая блокировка до обновления списка, либо не ТСПУ)» |
| не в реестре | жив | как обычно |
| список недоступен | любые | как обычно, пометка «реестр недоступен» |

Ключевое правило: **уверенность и класс вычисляются ровно как сейчас**. Реестр —
текстовая пометка, а не вес.

## 6. Контракт

### 6.1 Settings

```python
registry_enabled: bool = Field(default=True, alias="REGISTRY_ENABLED")
registry_refresh_s: int = Field(default=3600, alias="REGISTRY_REFRESH_S")
registry_url_ipsum: str = Field(default="https://antifilter.download/list/ipsum.lst", alias="REGISTRY_URL_IPSUM")
registry_url_ipsmart: str = Field(default="https://antifilter.download/list/ipsmart.lst", alias="REGISTRY_URL_IPSMART")
registry_cache_path: Path = Field(default=Path("/data/registry_cache.txt"), alias="REGISTRY_CACHE_PATH")
```

Плюс записи в `.env.example` и `compose.yaml`.

### 6.2 Факты и классификатор

- В `raw` каждого результата добавляется ключ `"registry": {listed, source, prefix, known}`.
  Записывается в `ProbeResult.raw` в `save_results` (модель БД не меняется: raw уже JSON).
- `classifier.classify()` **читает** этот ключ, но **не начисляет весов**. Единственное
  допустимое использование внутри классификатора — ничего. Пометка живёт в отчёте.
- `Classification` получает опциональное поле `registry_note: str = ""` — его заполняет
  `service.save_results` (не классификатор), чтобы рендеринг показал пометку.

### 6.3 Рендеринг

- `rendering.py`: в блок сносок — строка пометки реестра:
  - `listed` → `Адрес в реестре блокировок (источник, префикс): с высокой вероятностью под блокировкой; проверка зондами подтверждает/уточняет`
  - `not listed` + класс block_* → `В публичном реестре РКН адреса нет — см. оговорки`
  - `known=False` → `Реестр недоступен — пометка отсутствует`
- В черновик (`_draft_text`) — краткая пометка сразу после старта: «в реестре: да/нет».
- Disclaimer остаётся последним блоком; пометка реестра — до него.

### 6.4 Ограничения отчёта (оговорки, обязательные)

В пометке реестра всегда присутствует дата/возраст списка:

- `список от {timestamp}, возраст {N} ч` — если возраст > 24 ч, добавить
  `список устарел`.
- Стандартная оговорка: «membership в реестре — не факт блокировки: списки запаздывают
  на 5–15 минут относительно DPI-листов, содержат shared IP/CDN, и не все механизмы
  блокировки отражаются в публичном реестре».

## 7. Тесты

Новые тесты (`bot/tests/test_registry.py`):

1. Парсинг формата списка: строки с префиксами, пустые строки, комментарии/мусор —
   не падать, игнорировать.
2. `lookup(192.0.2.1)` → listed, если /24 цели есть в списке.
3. `lookup` для IPv6-цели → known=False (IPv6-список вне рамок этого плана).
4. Отказ загрузки → known=False, бот продолжает работать.
5. Кэш на диске: после рестарта без сети список поднимается из кэша.
6. `probes_for` не меняется от реестра: в реестре и вне — одинаковый набор зондов.

Тесты отчёта (`test_rendering.py`):

7. Пометка реестра присутствует в rich-сообщении и корректно формулируется для
   всех трёх состояний (listed / not listed / unknown).

Тесты потока (`test_db.py` или новый):

8. `save_results` кладёт `registry` в `raw` и заполняет `registry_note`.

## 8. Риски

- **Списки устаревают / расходятся с фильтрами.** Оговорка в отчёте обязательна.
- **Shared IP / CDN.** Один адрес обслуживает и заблокированные, и нет ресурсы;
  пометка «в реестре» не должна читаться как «весь контент на адресе заблокирован».
- **Объём памяти.** ~21k префиксов в виде `IPv4Network` — единицы МБ; приемлемо.
  Если измерения покажут иначе — перейти на пару `(int(network), int(mask))`.
- **Доступность antifilter.network.** Новый источник недоступен → бот деградирует
  до поведения без реестра; прогон никогда не блокируется ожиданием списка.
- **Юридическая/репутационная.** Проект по-прежнему observation-only: реестр —
  внешний источник данных, он указывается в отчёте явно, с датой и источником.
- **IPv6.** `ip6.lst` вне рамок: известные IPv6-цели получают `known=False`.

## 9. Порядок исполнения

1. `registry.py`: загрузка, парсинг, lookup, кэш, фоновое обновление.
2. Settings/env/compose.
3. Поток в `service.py`/`handlers.py`: lookup до прогона, `registry` в `raw`,
   `registry_note` в Classification/TargetReport, пометка в черновик.
4. Рендеринг: пометка в таблице/сносках.
5. Тесты по разделу 7.
6. Валидация: `pytest` весь зелёный; ручной прогон с живым агентом: цель из реестра
   (например, любой адрес из свежего `ipsum.lst`) и цель вне реестра.

## 10. Валидация

- `python -m pytest tests -q` — все старые + новые.
- `tools/integration_check.py`: сценарий «цель в реестре → пометка присутствует,
  класс по зондам» (без assert на класс: состав реестра живой).
- Ручной прогон в Telegram: адрес из реестра → пометка видна в черновике и отчёте.
