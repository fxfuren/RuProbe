# Модель ТСПУ для задач RuProbe

Рабочая выжимка по ТСПУ (технические средства противодействия угрозам) — ровно в том объёме,
который нужен боту проверки доступности IP, доменов и диапазонов.

Источники:

- [DanielLavrushin/tspu-docs](https://github.com/DanielLavrushin/tspu-docs) — разбор архитектуры
  и эксплуатации АСБИ/ТСПУ (сгенерирован по лекции, проверен вручную, возможны неточности);
- [Пожалуй, все что надо знать о ТСПУ](https://habr.com/ru/articles/1095490) (owenewans);
- [Как работают ТСПУ и DPI](https://habr.com/ru/articles/992232/) (DevRoad).

> Документ описывает **наблюдаемое поведение** сети, а не способы обхода. Техники обхода
> (фрагментация ClientHello, анти-DPI, туннелирование) сознательно вне рамок RuProbe.

---

## 1. Что такое ТСПУ и что из этого следует для проб

ТСПУ — комплекс оборудования на сети оператора связи, установленный **в разрыв канала**
(inline), под управлением ЦСУ (центральной системы управления). Состав:

| Компонент | Роль | Что важно для нас |
|---|---|---|
| Байпас | точка врезки, аппаратная защита канала | при отказе замыкает канал, трафик идёт мимо анализа |
| Балансировщик (EcoFilter Balancer / Eco Highway) | распределение трафика по фильтрам | хэш по `src IP, dst IP, IP proto`; одна сессия → одно ядро одного фильтра |
| Фильтр (EcoFilter + EcoDPI) | анализ и обработка трафика | именно здесь принимается решение о блокировке |
| Сегмент управления (VPN, SPFS, СПХД) | связь с ЦСУ, логи, списки | цикл распространения нового адреса в списках ~5–15 мин |

### 1.1. L2-прозрачность

ТСПУ работает на канальном уровне: у фильтров нет L3-интерфейсов в тракте передачи, MAC-адреса
не изучаются, кадр всегда выходит строго в парный порт (LAN ↔ WAN), заголовки инкапсуляции
(VLAN, MPLS, PPPoE) не снимаются и не модифицируются. Для оборудования оператора ТСПУ
неотличимо от отрезка кабеля.

Практические следствия для RuProbe:

1. **ТСПУ не видно в `traceroute`** как отдельный хоп — оно не отвечает и не увеличивает TTL.
   Отсутствие промежуточного хопа ничего не говорит о наличии ТСПУ.
2. **RTT до ТСПУ измерить нельзя.** Моделировать «задержку от ТСПУ» бессмысленно; можно
   измерять только задержку/потери end-to-end до цели.
3. **Нельзя прощупать фильтр снаружи.** Фильтр не генерирует трафик в data plane, у него
   нет IP-интерфейсов для инициации соединений. Значит, любые утверждения бота строятся
   исключительно на поведении целевого ресурса глазами абонента.
4. **Инкапсуляция может отличаться между операторами** (VLAN/QinQ, MPLS, PPPoE до BRAS,
   GTP-U в мобильных сетях). Это влияет на то, попадёт ли трафик под DPI вообще, а не
   только на наш слой.

### 1.2. Фильтрация — это конвейер, а не одна проверка

Пакет на LAN-порту фильтра проходит последовательно четыре гейта:

```
пакет → (1) это IP-пакет? → (2) попал в ACL и пул? → (3) попал в DPI-лист по IP? → (4) движок DPI
         нет → прозрачно в парный порт   нет → прозрачно   нет → прозрачно      pass / drop
```

1. **«IP-пакет или нет»** — не-IP кадры (в т.ч. keep-alive балансировщика) уходят без обработки.
2. **ACL → пул.** ACL определяет, какой трафик подлежит анализу; отобранное попадает в пул
   (в проекте ТСПУ пул типа `fake`, то есть **без NAT** — фильтр не меняет адреса).
3. **DPI-лист по IP-подсетям.** Если адреса пакета не попадают в обработку листа —
   пакет пропускается без анализа. Управляется параметрами `IP` / `No IP` / `No IP Remote`.
4. **Движок DPI.** Только здесь принимается решение `pass` / `drop`, плюс действия блокировки.

**Главный вывод для бота:** недоступность и «недоступность из-за ТСПУ» — разные вещи.
Трафик может не дойти до DPI вообще (не попал в пул/лист, другой оператор, другое место
установки). Классификация должна быть вероятностной по сигнатурам, а не вердиктом.

### 1.3. Режим без NAT

В проекте ТСПУ NAT не используется: `local IP == global IP`, фильтр ничего не транслирует.
Для нас это означает, что адрес, который видит оператор, — это адрес, который отправил
агент (до CGNAT оператора) либо адрес из NAT-пула (после CGNAT). Отсюда важность точки
установки (раздел 5).

## 2. Четыре класса отказа

Это ядро модели данных RuProbe: каждый результат пробы должен сопоставляться с одним
из классов (или с «недоступность не по ТСПУ»).

### 2.1. Тупая блокировка по L3/L4

**Механика.** Правило отбрасывает пакеты по IP-адресу, подсети, L4-порту или транспорту
целиком (например, весь UDP). Содержимое пакета не анализируется вообще.

**Почему бесполезно менять запрос.** Зашифровать, сжать, разбить на фрагменты — адрес,
порт и транспорт остаются теми же. Правило отбрасывает подключение целиком.

**Наблюдаемые сигнатуры:**

- SYN уходит, ответа нет; TCP-хендшейк не завершается;
- то же поведение на всех портах данного IP;
- `curl`, браузер, любое приложение — одинаково;
- недоступность не зависит от SNI, TLS-параметров, содержимого запроса;
- часто затрагивает **диапазон/CDN**, а не отдельный адрес (важно для проб по соседним IP).

**Как отделять от «ресурс не работает»:** ресурс жив на другом IP из той же AS или на
другом IP того же сервиса; при этом недоступность стабильна и воспроизводима.

### 2.2. Умная блокировка по признакам (SNI)

**Механика.** IP, порт и транспорт разрешены. DPI собирает сессию (5-tuple), реассемблирует
TCP-поток, парсит ClientHello и извлекает SNI. Далее сравнивает с DPI-листами.

Важные особенности, которые надо учитывать:

- **Реассемблирование.** Простой разрез ClientHello на два сегмента не помогает — фильтр
  собирает поток по sequence-номерам. Это значит, что «дошёл ли ClientHello» надо проверять
  не по факту отправки, а по факту отсутствия обрыва.
- **Блокировка возможна только по домену, целиком.** SNI не содержит пути и URL. Запись вида
  `https://example.com/foo` в списке заблокирует весь домен.
- **Точность только для HTTP.** Для открытого HTTP доступны и Host, и путь, и URL — то есть
  блокировка до конкретной страницы. Для HTTPS — только домен.
- **ECH.** Encrypted Client Hello скрывает внутренний ClientHello, но остаётся виден сам
  признак использования ECH. ТСПУ может запрещать такие соединения целиком (практика
  известна для Cloudflare: диапазон IP + внешнее SNI + расширение ECH).

**Ключевой различитель — RST против молчаливого drop.** В проекте ТСПУ параметр
`send RST off` **всегда включён**: при блокировке распознанных протоколов TCP Reset
**не отправляется**, соединение отбрасывается молча и «висит» до тайм-аута. Причина
документирована: при получении RST приложение мгновенно переподключается в цикле, что
создаёт избыточную нагрузку на фильтр.

Следствие для бота: **мгновенный RST — скорее аномалия**, чем штатное поведение ТСПУ
(возможен при `behavior: block` для HTTP-редиректа / HTTPS-Reset по конкретным листам,
либо это не ТСПУ вовсе). А вот «SYN-ACK получен, ClientHello отправлен, дальше тишина
до таймаута» — характерная сигнатура ТСПУ.

**Наблюдаемые сигнатуры:**

- TCP-хендшейк завершается успешно (SYN → SYN-ACK → ACK);
- ClientHello уходит, ответа нет; соединение висит до таймаута (не RST);
- принудительная установка **другого** SNI на тот же IP/порт — работает;
- TLS-параметры (наборы шифров, расширения, порядок) могут влиять на результат —
  известны случаи блокировки по отпечатку клиента (JA3/JA3S), когда браузер открывает
  сайт, а приложение — нет, и смена наборов шифров помогает;
- поведенческие признаки (размеры первых пакетов, тайминги, объём и направление трафика)
  могут блокироваться независимо от SNI.

### 2.3. Деградация протокола (capacity 0–100)

**Механика.** Вместо блокировки задаётся `capacity` для протокола: 0 — полная блокировка,
100 — полный пропуск, 1–99 — **дроп пакетов с заданной вероятностью** в рамках сессии.

**Почему это коварно.** TCP компенсирует потери повторной передачей и снижает окно,
то есть потери маскируются под перегрузку. Документация прямо указывает: заметная
деградация начинается при `capacity` примерно **2–10**; при `capacity ≈ 5` задержки
доставки сообщений могут достигать десятков секунд. Особенно эффективно это для
голосовых и видеозвонков.

**Наблюдаемые сигнатуры:**

- соединение устанавливается, TLS-handshake проходит, короткий `HEAD`/`GET` отвечает 200;
- скорость передачи падает в разы относительно ожидаемой;
- ненормальный паттерн retransmission (много повторов, «пила» окна);
- короткий запрос работает, длинная передача зависает;
- пинг (ICMP) часто в норме — страдает именно TCP/UDP-передача данных;
- результат плавает от прогона к прогону (вероятностный дроп).

**Прямое следствие для архитектуры:** проба «доступности» по факту connect/HTTP-кода
**будет систематически врать**. Обязателен отдельный зонд измерения пропускной способности
на нескольких секундах передачи, иначе класс 2.3 бот просто не увидит.

### 2.4. DNS-вмешательство

**Механика.** Отдельный слой, не связанный с DPI по SNI. Оператор может настроить запрет на
своём резолвере либо вмешаться в запрос к чужому (в т.ч. перехват порта 53).

**Наблюдаемые сигнатуры (в порядке частоты):**

| Сигнатура | Что видит агент |
|---|---|
| Подмена адреса | вместо реального A/AAAA отдаётся заглушка или нерабочий адрес |
| `NXDOMAIN` | домен «не существует» |
| `REFUSED` | резолвер отклонил запрос |
| `SERVFAIL` | разрешение не удалось |
| Молчаливый drop | ответа нет, клиент ждёт и повторяет; в итоге timeout |

Важно: у DoH/DoT скрыт **вопрос**, но не **факт** соединения — у них свои отпечатки, и такое
соединение само проходит проверку DPI. DNS через туннель скрывает и вопрос, и содержимое,
но снаружи остаётся соединение с сервером туннеля.

**Следствие:** resolve надо делать **независимо и параллельно** от connect-пробы, иначе
невозможно отличить «домен не резолвится» от «IP заблокирован». Полезно также сравнивать
ответ локального резолвера, публичного резолвера и DoH — расхождение уже само по себе сигнал.

## 3. Таблица зондов

Минимальный набор, покрывающий четыре класса. «Зонд» — атомарная проверка с одним
наблюдаемым результатом; классификация собирается из совокупности зондов.

| Зонд | Что проверяет | Что различает | Класс |
|---|---|---|---|
| DNS resolve (системный + публичный) | ответ резолвера | подмена / NXDOMAIN / REFUSED / SERVFAIL / drop | 2.4 |
| DNS resolve через DoH | ответ шифрованного резолвера | расхождение с открытым DNS | 2.4 |
| TCP connect на целевой порт | SYN → SYN-ACK / RST / timeout | живость, время до отказа | 2.1, 2.2 |
| TCP connect на альтернативные порты того же IP | доступность хоста вне правил по порту | правило по порту vs по IP | 2.1 |
| TLS ClientHello с заданным SNI, без завершения handshake | проходит ли ClientHello | SNI-блокировка | 2.2 |
| TLS ClientHello с **другим** SNI на тот же IP | контрольная проба | блокировка по домену vs по адресу | 2.2 |
| Полный TLS handshake + HTTP(S) запрос | сквозная доступность, RST vs timeout | штатный ТСПУ-дроп vs аномалия | 2.2 |
| Загрузка N МБ за T секунд | пропускная способность, retransmission | деградация capacity | 2.3 |
| UDP probe / QUIC Initial | доступность UDP и QUIC | блокировка транспорта, QUIC-лист | 2.1, 2.2 |
| ICMP echo | базовая живость сети | «недоступность в норме», маршрут | — |
| Пинг соседних IP из /24, /16, AS | доступность соседей | адресное правило vs префикс/CDN vs сеть | 2.1 |

Практические замечания:

- **Контрольная проба обязательна.** Без «того же IP, но другого SNI» и без «того же
  домена, но другого IP» нельзя развести класс 2.2 и класс 2.1.
- **RST vs timeout фиксируется явно**, как отдельное поле результата, а не как «ошибка».
- **Проба на соседние адреса** («режут не сайты, а целые сети») хорошо отделяет запрет
  конкретного адреса от запрета префикса; это тот случай, когда простой перебор /24
  даёт гораздо больше информации, чем один идеально сделанный зонд.
- **`show dpi match` недоступен снаружи.** Это инструмент инженера на фильтре (по IP или
  URL, проверка по всем DPI-листам). Бот не может его вызвать — он работает только
  с внешне наблюдаемыми сигнатурами.

## 4. Модель точки наблюдения

**Провайдер — это не метаданные пробы, а первичный ключ измерения.**

Обоснование: ТСПУ стоит у каждого оператора отдельной площадкой; DPI-листы, значения
`capacity`, набор распознаваемых протоколов, момент обновления списков и даже точка
установки (до BRAS / до CGNAT / после CGNAT / on-a-stick) различаются. Один и тот же
ресурс штатно ведёт себя по-разному у разных операторов — это описано в документации
напрямую.

Отсюда:

- Агент привязывается к паре **(регион, оператор)** и поставляет пробы в общий бэкенд.
- Результат пробы без точки наблюдения не имеет смысла и не должен попадать в отчёты.
- «Пока один регион и провайдер» — это конфигурация, а не архитектурное допущение:
  модель должна допускать N провайдеров на регион (проверка «с разных опсосов») и N
  регионов без изменения схемы данных.
- Разные операторы одного региона сравнимы: расхождение вердиктов между ними —
  самостоятельный сигнал.

### 4.1. Где стоит ТСПУ и как это влияет на диагностику

| Точка установки | Особенность |
|---|---|
| До BRAS (абоненты → терминация) | есть PPPoE-инкапсуляция; в мобильных сетях GTP-U может не разбираться |
| После BRAS, до CGNAT | **наиболее удобная точка:** нет PPPoE, видны серые адреса абонентов |
| После CGNAT | видны только адреса NAT-пула; связать абонента с сессией сложно |
| on-a-stick | трафик может проходить через ТСПУ **дважды**, в разной ориентации |

Для RuProbe существенно: агенту важно знать, выходит ли он из-под NAT оператора и является
ли адрес серым. Это влияет на интерпретацию «недоступно у всех абонентов оператора» и на
то, можно ли сопоставлять пробы между узлами.

### 4.2. Что происходит с новым адресом

Блокировка протоколов двухстадийная: фильтр распознаёт сессию (`behavior: ignore`) и
отправляет протокольный лог на SPFS → ЦСУ; ЦСУ очищает данные от ложных срабатываний
и формирует списки IP+порт; списки загружаются обратно на фильтры (HTTP, отдельный
DPI-лист с `behavior: block`) и на Eco Highway (BGP, тип Б). Полный цикл — **~5–15 минут**.

Следствия:

- **Результат зависит от времени.** Ресурс может работать сейчас и перестать через
  15 минут — это ожидаемое поведение, а не флейк бота.
- **Существующие сессии не рвутся** до обновления списка.
- Умная блокировка со временем превращается в тупую: сначала запрет по SNI, потом
  IP попадает в список и блокируется уже по адресу. Поэтому «сменить протокол на том же
  сервере» перестаёт помогать, и проба должна это уметь заметить.

## 5. Границы применимости модели

Честные оговорки, которые надо держать в коде и в отчётах:

1. **Документация tspu-docs сгенерирована по лекции** и содержит авторскую оговорку
   о возможных неточностях. Это не первичная документация производителя.
2. **Статья на Хабре построена на упрощении** «тупая/умная блокировка». Упрощение полезно
   для объяснения, но на практике классы смешаны.
3. **`send RST off`, `capacity 2–10`, цикл 5–15 минут** — описание конкретного проекта
   и конкретных тестов (в т.ч. в Сургуте), а не гарантия поведения любого оператора.
   Настройки у разных операторов отличаются.
4. **ТСПУ постоянно борется с ложными срабатываниями** через двухстадийную блокировку и
   обновление сигнатур. Значит, бот не должен выдавать детерминированный вердикт
   («заблокировано РКН») — только вероятностную классификацию по сигнатурам с указанием
   точки наблюдения, времени и набора сработавших зондов.
5. **«Обход» вне рамок.** Модель описывает наблюдение доступности; техники обхода
   (фрагментация, анти-DPI, туннели) в RuProbe не реализуются.

## 6. Что из этого следует для кода

Короткий список требований, вытекающих из модели:

1. **Один результат — не один замер.** Классификация собирается из набора зондов,
   каждый зонд возвращает структурированный факт, а не булево «доступно».
2. **RST и timeout — разные события**, оба фиксируются явно.
3. **Молчаливый drop после успешного SYN-ACK** — приоритетная сигнатура ТСПУ.
4. **Контрольные пробы** (другой SNI на том же IP, тот же домен на другом IP, соседние
   адреса подсети) обязательны для разведения классов.
5. **Отдельный зонд throughput** — иначе деградация не детектируется.
6. **DNS-слой независим от connect-слоя**, resolve выполняется параллельно.
7. **Точка наблюдения (регион, оператор) — часть первичного ключа результата.**
8. **Вердикт всегда вероятностный**, с указанием сработавших сигнатур и времени замера,
   без категоричных утверждений о причине.
