Зафиксированные версии и границы применимости. Проверено 2026-11-11.

## 1. Агент (зонды) — Go 1.27.4

| Параметр | Значение |
|---|---|
| Версия | **go1.27.4** (актуальная стабильная) |
| Дата релиза | 2026-11-10 |
| Источник проверки | `https://go.dev/VERSION?m=text` |
| Ветка 1.27 | выпущена 2026-08-19 |
| Предыдущая поддерживаемая | 1.26.11 |

**Почему именно 1.27.4, а не любая 1.27.x.** 1.27.3 и 1.27.4 — релизы с исправлениями
безопасности:

- 1.27.3 (2026-10-19) — `crypto/x509` (CVE-2026-111943);
- 1.27.4 (2026-11-10) — `net/http`, `crypto/tls`, `crypto/rsa`, `crypto/hkdf`, `crypto/fips140`,
  плюс компилятор, линкер и `go` command.

Для агента, который делает TLS-пробы и HTTP-запросы, исправления в `net/http` и `crypto/tls`
релевантны напрямую. Ставить 1.27.0–1.27.2 не следует.

Отдельно: в 1.27 появились **generic methods** — полезно для абстракций над зондами.
Поэтому целевая ветка именно 1.27, а не 1.26 (1.26 остаётся поддерживаемой, но не даёт
новых возможностей языка).

**Установка / обновление** (на машине стоит go1.26.4 — нужно обновить):

```powershell
winget install GoLang.Go
```

либо MSI `go1.27.4.windows-amd64.msi` с `https://go.dev/dl/`.

**Проверка:**

```powershell
go version   # ожидается go1.27.4
```

**В `go.mod`:**

```
go 1.27.4
```

## 2. Интерфейс (Telegram-бот) — aiogram 3.31.0

### 2.1. Важное уточнение по версиям

В задаче указано «aiogram 10.3». Такой версии **не существует**. Перепутаны два разных
номерa:

| Что | Номер | Пояснение |
|---|---|---|
| **aiogram** (Python-библиотека) | **3.31.0** | актуальная версия, релиз 2026-08-26 |
| **Telegram Bot API** | **10.3** | версия API Telegram, поддерживается aiogram 3.31.0 |
| Последний aiogram до этого | 3.22.0 | релиз 2025-08-17 |

То есть «10.3» и «10.2» — это версии **Bot API**, а не aiogram. Установка `aiogram 10.3`
приведёт к ошибке «no matching distribution».

**Правильная установка:**

```powershell
pip install aiogram==3.31.0
```

**Требования по Python:** `>=3.10, <3.15`. На машине Python 3.12.10 — подходит.
Верхняя граница `<3.15` важна: на Python 3.15 установка не пройдёт.

Актуальная линейка для ориентира: 3.27.0, 3.28.x, 3.29.x, 3.30.0 (Bot API 10.2),
**3.31.0 (Bot API 10.3)**.

### 2.2. Rich messages

Rich messages появились как полноценный структурированный формат вывода и полностью
поддерживаются в 3.31.0 (Bot API 10.3). Это ровно то, что нужно для отчётов по пробам.

**Ключевые отличия от обычных сообщений:**

- **Нет parse mode.** В `InputRichMessage` заполняется **ровно одно** из трёх полей:
  `markdown`, `html` или `blocks`. Одновременно нельзя.
- `blocks` — самое новое (Bot API 10.2), вообще без разметки: список объектов-блоков.
- **Лимиты:** до 32768 UTF-8 символов в тексте (против 4096 у обычного сообщения),
  до 500 блоков, до 16 уровней вложенности, до 50 медиавложений, до 20 колонок в таблице.

**Что поддерживается (важно для отчётов RuProbe):**

- заголовки, абзацы, разделители, списки и todo-списки;
- вложенное inline-форматирование (жирный, курсив, подчёркивание, зачёркивание, спойлер,
  код, нижний/верхний регистр);
- **таблицы** с выравниванием, подписями, границами, «полосатым» стилем, объединением
  колонок и строк;
- медиа-блоки (фото, видео, аудио) с подписями и авторством;
- цитаты, **сворачиваемые блоки `details`**, якоря и внутренние ссылки;
- сноски;
- полный LaTeX (inline и блочный).

**Отправка:**

```python
from aiogram.types import InputRichMessage

# Markdown
await message.answer_rich(
    rich_message=InputRichMessage(markdown="# Заголовок\n\n**готово**")
)

# HTML — когда нужен точный контроль над форматированием
await message.answer_rich(
    rich_message=InputRichMessage(html="<h1>Отчёт</h1><p>Цель <b>недоступна</b></p>")
)

# Blocks — без разметки вообще
await message.answer_rich(
    rich_message=InputRichMessage(blocks=[...])
)
```

Шорткаты: `Message.answer_rich()`, `Message.reply_rich()`.
Напрямую: `bot.send_rich_message(...)`. Тип метода: `SendRichMessage`.

**Когда что использовать:**

| Задача | Метод |
|---|---|
| «Проверка запущена», «Готово», короткая реплика | `sendMessage` |
| Отчёт по диапазону IP: таблица результатов, сигнатуры, тайминги | `sendRichMessage` |
| Длинный структурированный вывод с заголовками и сносками | `sendRichMessage` |

Rich не заменяет обычные сообщения — это два инструмента под разные задачи. У обычных
сообщений остаются свои эксклюзивные возможности (например, частичное цитирование
и пересылка цитаты).

**Приём rich-сообщений** (может понадобиться, если боту будут присылать структурированные
запросы): у `Message` есть поле `rich_message` типа `RichMessage` — это список блоков
`blocks`, у каждого блока есть `type` (`heading`, `paragraph`, `table`, `list`, `photo`,
`slideshow`, `collage`, `footer` и др.), а текстовые блоки несут дерево `RichText`.
Голый текст извлекается рекурсивным обходом дерева.

**Стриминг частичного вывода:** `sendRichMessageDraft` (`bot.send_rich_message_draft(...)`)
отправляет промежуточный вариант с `draft_id`; черновик живёт 30 секунд и служит превью,
а по завершении нужно вызвать `sendRichMessage` для финального результата. Полезно при
долгих проверках диапазонов — но это необязательная оптимизация, не базовый сценарий.

## 3. Архитектурное следствие

**Go 1.27.4 — агент (зонды, горячий путь, конкурентность и таймауты).**
**Python 3.12 + aiogram 3.31.0 — интерфейс (Telegram, rich messages для отчётов).**

Такое разделение соответствует требованию «чтобы всё быстро прогонялось»: нагрузка
сетевых проб и параллельных таймаутов остаётся в Go, а на Python лежит только диалоговый
слой, где производительность не критична.

Открытый вопрос, который стоит решить до написания кода (влияет на границы модулей):
интерфейс и агент — это **два процесса на одной машине** (Go как демон-зонд, Python как
фронтенд, связь локально) или **агент находится в отдельной точке наблюдения** (другой
регион/оператор) и общается с центром по сети? Во втором случае с первого дня нужны
регистрация, аутентификация и привязка к паре «регион + оператор» из раздела 4
`docs/tspu-model.md`, плюс очередь проб и буферизация результатов при недоступности центра.
